# Isolate Tenants with Row-Level Security (RLS)

This guide shows how to enforce multi-tenant Row-Level Security (RLS) on `auditstream.changes` on Auditstream v0.1.x, including managed PostgreSQL services (Amazon RDS, Neon, and Supabase).

> **Why `--tenant` alone is not tenant isolation:** `auditstream history --tenant` and `auditstream export --tenant` filter self-asserted `actor.tenant` and `actor.onBehalfOf.tenant` metadata. They omit rows where `actor` is `NULL`, `actor_source = 'invalid'`, or `actor_source = 'jwt'`, and do not enforce database-level authorization. Use PostgreSQL RLS whenever application queries read `auditstream.changes` across tenants.

## Prerequisites

- **Auditstream installed:** Apply the migration generated by `auditstream init` first so `auditstream_owner` and `auditstream.changes` already exist.
- **CLI version:** Use Auditstream CLI **`v0.1.1+`** for parent-only `SELECT` verification and the built-in `verify` / `export` RLS guards (`v0.1.0` queried `ONLY auditstream.changes_default` directly).
- **Ownership and elevation:** `auditstream.changes`, all monthly partitions, and helper functions are owned by the `NOLOGIN` role `auditstream_owner`. Only `auditstream_owner` or a superuser can enable RLS, create policies, or create indexes on `auditstream.changes`:
  - **PostgreSQL 16+ (managed non-superuser):** Connect with a role holding `ADMIN OPTION` on `auditstream_owner` (typically the same `CREATEROLE` migration role that ran `auditstream init`). Do not run these snippets inside a prior `SET ROLE` session without restoring that role or passing `GRANTED BY`.
  - **PostgreSQL 15 (managed non-superuser):** Omit `WITH INHERIT FALSE, SET TRUE` from the temporary `GRANT auditstream_owner TO migrator_role;` statement and revoke before committing.
  - **Superuser:** Omit the temporary `GRANT`/`REVOKE` statements and run `SET LOCAL ROLE auditstream_owner;` (or `SET ROLE auditstream_owner;` outside transactions) directly.
  - Leaving permanent `INHERIT` or `SET` membership on `auditstream_owner` (or any membership on PostgreSQL 15 or non-`CREATEROLE` roles) causes [`auditstream verify`](../reference/cli/verify.md) to fail with `unsafe_privileges`.
- **Placeholders:** Substitute your migration role for `migrator_role`, your database name for `<your_db>`, unique passwords for `<*-password>`, your tenant column name if it differs from `tenant_id` (matching PostgreSQL's `to_jsonb` text form, such as lowercase canonical UUIDs), and your custom `--schema` name for `auditstream` if non-default. Always keep `auditstream_owner` literal.

## Step 1: Create dedicated `NOBYPASSRLS` roles

PostgreSQL 15 and older restrict `BYPASSRLS` to superusers, and Amazon RDS does not grant `BYPASSRLS` to customer admin roles (`rds_superuser`).
Even where a provider allows `BYPASSRLS`, dedicated `NOSUPERUSER NOBYPASSRLS NOINHERIT` roles with explicit policies work identically across Amazon RDS, Neon, Supabase, and self-hosted PostgreSQL 15–19 with least privilege.

> **Neon and Supabase warning:** Default admin roles (`neondb_owner`, `postgres`, `service_role`) and roles created via the Neon Console, CLI, or API (`neon_superuser`) carry `BYPASSRLS` and silently bypass all RLS policies. Always create `app_user` via SQL with `NOBYPASSRLS` and connect your runtime application with that role.

```sql
CREATE ROLE app_user
  LOGIN PASSWORD '<app-password>'
  NOSUPERUSER NOCREATEDB NOCREATEROLE NOBYPASSRLS NOINHERIT;

CREATE ROLE auditstream_exporter
  LOGIN PASSWORD '<exporter-password>'
  NOSUPERUSER NOCREATEDB NOCREATEROLE NOBYPASSRLS NOINHERIT;

CREATE ROLE auditstream_verify
  LOGIN PASSWORD '<verify-password>'
  NOSUPERUSER NOCREATEDB NOCREATEROLE NOBYPASSRLS NOINHERIT;

GRANT CONNECT ON DATABASE <your_db> TO app_user, auditstream_exporter, auditstream_verify;
```

*(Skip `CREATE ROLE app_user` if your application already uses a dedicated `NOSUPERUSER NOBYPASSRLS` role; still grant it the least-privilege table permissions your application needs on your audited tables.)*

## Step 2: Enable row-data RLS and create policies

This row-data RLS pattern derives tenant ownership directly from captured row snapshots (`after->>'tenant_id'` and `before->>'tenant_id'`) rather than self-asserted `actor->>'tenant'` metadata.

```sql
BEGIN;
-- Bound lock waits: ENABLE ROW LEVEL SECURITY and CREATE POLICY acquire ACCESS EXCLUSIVE locks.
SET LOCAL lock_timeout = '5s';

-- Managed PostgreSQL 16+ migrator with ADMIN OPTION on auditstream_owner
-- (omit GRANT/REVOKE if superuser; on PostgreSQL 15 use: GRANT auditstream_owner TO migrator_role;)
GRANT auditstream_owner TO migrator_role WITH INHERIT FALSE, SET TRUE;
SET LOCAL ROLE auditstream_owner;

-- 1. Grant parent-only SELECT to runtime, exporter, and verify roles.
--    NEVER run: GRANT SELECT ON ALL TABLES IN SCHEMA auditstream TO app_user;
GRANT USAGE ON SCHEMA auditstream TO app_user, auditstream_exporter, auditstream_verify;
GRANT SELECT ON auditstream.changes TO app_user, auditstream_exporter, auditstream_verify;
-- Grant EXECUTE on log_event ONLY when app_user is restricted to trusted server code (see note below).
GRANT EXECUTE ON FUNCTION auditstream.log_event(text, jsonb, jsonb) TO app_user;

-- 2. Enable RLS on the parent table ONLY.
--    NEVER enable FORCE ROW LEVEL SECURITY on auditstream.changes or its partitions.
ALTER TABLE auditstream.changes ENABLE ROW LEVEL SECURITY;

-- 3. Dedicated unfiltered SELECT policies for exporter and verify roles
--    (managed-Postgres safe; no BYPASSRLS attribute required).
CREATE POLICY changes_exporter_select
  ON auditstream.changes
  AS PERMISSIVE
  FOR SELECT
  TO auditstream_exporter
  USING (true);

CREATE POLICY changes_verify_select
  ON auditstream.changes
  AS PERMISSIVE
  FOR SELECT
  TO auditstream_verify
  USING (true);

-- 4. Row-data tenant policy scoped strictly TO app_user (NEVER TO PUBLIC).
CREATE POLICY changes_tenant_select
  ON auditstream.changes
  AS PERMISSIVE
  FOR SELECT
  TO app_user
  USING (
    (
      (source = 'db' AND (
        (schema_name = 'public' AND table_name IN ('invoice', 'line_item'))
      ))
      OR (source = 'app' AND op IN ('invoice.exported', 'invoice.sent'))
    )
    AND (
      CASE
        WHEN source = 'db' AND op = 'INSERT' THEN after->>'tenant_id'
        WHEN source = 'db' AND op = 'DELETE' THEN before->>'tenant_id'
        WHEN source = 'db' AND op = 'UPDATE'
          AND (before->>'tenant_id') IS NOT DISTINCT FROM (after->>'tenant_id')
          THEN after->>'tenant_id'
        WHEN source = 'app' THEN actor->>'tenant'
        ELSE NULL
      END
    ) = NULLIF(pg_catalog.current_setting('app.tenant', true), '')
  );

SET LOCAL ROLE NONE;
REVOKE auditstream_owner FROM migrator_role;
COMMIT;
```

### Why every clause matters

- **Never use `FORCE ROW LEVEL SECURITY`:** `auditstream.capture()` and `auditstream.log_event()` execute as `SECURITY DEFINER` owned by `auditstream_owner`. `FORCE ROW LEVEL SECURITY` subjects `auditstream_owner` to RLS with no `INSERT` policy, aborting every audited write with SQLSTATE `42501` (`new row violates row-level security policy for table "changes"`). `auditstream verify` flags `FORCE ROW LEVEL SECURITY` on `changes` or any child partition as `forced_rls` (`error`).
- **Derive DB-row ownership from row data, not `COALESCE(actor->>'tenant', ...)`:** Actor fields in SQL comments or `set_config('auditstream.actor', ...)` are caller-supplied. Reading `after->>'tenant_id'` and `before->>'tenant_id'` ties visibility to the actual row stored by PostgreSQL, preventing a forged `actor.tenant` from exposing another tenant's table rows.
- **Allowlist `(schema_name, table_name)` pairs:** Never match bare `table_name` alone (for example `table_name = 'invoice'`), which collides across schemas such as `internal.invoice`. Explicit allowlists also hide internal audited tables (such as `public.fraud_reviews`) from tenants by default.
- **Guard cross-tenant `UPDATE`s:** `(before->>'tenant_id') IS NOT DISTINCT FROM (after->>'tenant_id')` fails closed whenever a row moves between tenants or changes between `NULL` and a tenant ID. Neither tenant sees the transfer row; only administrators and `auditstream_exporter` see it.
- **Keep `TRUNCATE` admin-only and lock down `source = 'app'`:** `TRUNCATE` has `NULL` row images, falls through to `ELSE NULL`, and stays admin-only. For `source = 'app'`, `auditstream.log_event()` runs `SECURITY DEFINER` and resolves `actor.tenant` from caller-writable `set_config('auditstream.actor', ...)` / SQL comments without checking `app.tenant`:
  - Include the `source = 'app'` branch (and `GRANT EXECUTE` on `log_event`) **only** when `app_user` runs exclusively behind trusted server code that sets `actor.tenant` from authenticated session state.
  - If `app_user` is directly reachable by untrusted clients (such as Supabase PostgREST or Neon Authorize `authenticated` roles), revoke `EXECUTE` on `auditstream.log_event` from that role (or wrap it in a `SECURITY DEFINER` helper that pins `actor.tenant` / `data.tenant_id` to verified tenant context) and omit the `source = 'app'` branch from both `changes_tenant_select` and Step 3's expression indexes to prevent cross-tenant audit injection.
  - Note also that `actor_source = 'jwt'` populates only `type` and `id` (no `tenant`), so `log_event()` calls relying on Supabase JWT fallback stay hidden under `actor->>'tenant'`.
- **Wrap `current_setting` in `NULLIF(..., '')`:** After a transaction-local `set_config('app.tenant', ..., true)` commits on a pooled backend, PostgreSQL resets the placeholder GUC to `''` rather than `NULL`. `NULLIF(pg_catalog.current_setting('app.tenant', true), '')` turns both unset and `''` into `NULL`, failing closed (`0` rows).
- **Scope tenant policies `TO app_user`, never `TO PUBLIC`:** PostgreSQL rewrites and plans every applicable `PERMISSIVE` policy on a role. A `TO PUBLIC` tenant policy also applies to `auditstream_verify`, causing `auditstream verify` to warn `rls_hides_default_partition`. Ensure zero `RESTRICTIVE` policies covering `SELECT` (`FOR SELECT` or `FOR ALL`) apply to `auditstream_exporter` or `auditstream_verify`.
- **Never grant privileges on child partitions:** Never run `GRANT SELECT ON ALL TABLES IN SCHEMA auditstream TO app_user`. Direct reads on child partitions bypass parent-table RLS; `auditstream verify` flags any non-owner child-partition grant as `unsafe_privileges`.

## Step 3: Index tenant feeds (and avoid anti-patterns)

Without a tenant index, a tenant activity feed (`ORDER BY occurred_at DESC, id DESC LIMIT 50`) performs a sequential scan plus sort across every unpruned monthly partition.

Measured across PostgreSQL 15.20, 17.12, and 19.0 on 500,000 rows across 100 tenants and 3 monthly partitions under RLS:

| Index strategy | Activity Feed (`LIMIT 50`) | Buffers read | Query plan |
| --- | ---: | ---: | --- |
| No tenant index | `33.6–44.8 ms` | `18k–36k` | Parallel Seq Scan + Sort |
| AST-matched row-data expression B-tree | **`0.154–0.178 ms`** | **`68`** | **`189–291×` faster**; `Merge Append` + `Index Scan`, zero sort |

> **Anti-pattern — do not use `GIN (after jsonb_path_ops)`:** A GIN index on `after` adds `+27–30%` write overhead, cannot satisfy `ORDER BY occurred_at DESC, id DESC LIMIT 50` without fetching and sorting all matching rows, and misses `DELETE` events where `after IS NULL`.

### Create the AST-identical partial expression B-tree

PostgreSQL uses an expression index for an RLS `USING` clause only when the indexed expression and partial `WHERE` predicate match the policy's parsed AST **exactly**.
Even minor AST drift — such as swapping `(after->>'tenant_id') IS NOT DISTINCT FROM (before->>'tenant_id')` or altering the allowlist predicate — silently drops index usage and falls back to `Seq Scan`.

*(Whenever you add or remove an allowlisted table later — or if you omitted the `source = 'app'` branch in Step 2 — update `changes_tenant_select`, rebuild your expression index(es) with the matching `CASE` and `WHERE` clauses, and update any `SECURITY DEFINER` lookup wrapper together so the AST stays identical.)*

- **Empty or newly initialized table:** Omit `ONLY` and `CONCURRENTLY`, and run `CREATE INDEX changes_tenant_feed_idx ON auditstream.changes (...) WHERE (...);` inside the same `BEGIN; ... COMMIT;` block as Step 2.
- **Live production table (zero-downtime online build):** Run on a **direct (non-pooled) connection**, because `CREATE INDEX CONCURRENTLY` cannot run inside a transaction block and session-level `SET ROLE` is unsafe behind transaction-mode poolers.

```sql
-- 0. List every existing child partition (including changes_default) before starting:
SELECT c.relname
  FROM pg_catalog.pg_inherits i
  JOIN pg_catalog.pg_class p ON p.oid = i.inhparent
  JOIN pg_catalog.pg_namespace pn ON pn.oid = p.relnamespace
  JOIN pg_catalog.pg_class c ON c.oid = i.inhrelid
 WHERE pn.nspname = 'auditstream' AND p.relname = 'changes'
 ORDER BY c.relname;
```

```sql
-- Direct (non-pooled) connection only; outside a transaction block.
-- Omit GRANT/REVOKE if superuser; on PostgreSQL 15 use: GRANT auditstream_owner TO migrator_role;
GRANT auditstream_owner TO migrator_role WITH INHERIT FALSE, SET TRUE;
SET ROLE auditstream_owner;

-- 1. Register the parent index definition with a bounded lock_timeout.
--    ON ONLY avoids locking existing child partitions, but briefly takes a metadata ShareLock on changes.
SET lock_timeout = '5s';
CREATE INDEX changes_tenant_feed_idx
  ON ONLY auditstream.changes (
    (
      CASE
        WHEN source = 'db' AND op = 'INSERT' THEN after->>'tenant_id'
        WHEN source = 'db' AND op = 'DELETE' THEN before->>'tenant_id'
        WHEN source = 'db' AND op = 'UPDATE'
          AND (before->>'tenant_id') IS NOT DISTINCT FROM (after->>'tenant_id')
          THEN after->>'tenant_id'
        WHEN source = 'app' THEN actor->>'tenant'
        ELSE NULL
      END
    ),
    occurred_at DESC,
    id DESC
  )
  WHERE (
    (source = 'db' AND (
      (schema_name = 'public' AND table_name IN ('invoice', 'line_item'))
    ))
    OR (source = 'app' AND op IN ('invoice.exported', 'invoice.sent'))
  );
RESET lock_timeout;

-- 2. Repeat CONCURRENTLY + ATTACH for EVERY partition returned by query 0
--    (every changes_YYYY_MM partition AND changes_default). Example for one partition:
CREATE INDEX CONCURRENTLY changes_2026_11_tenant_feed_idx
  ON auditstream.changes_2026_11 (
    (
      CASE
        WHEN source = 'db' AND op = 'INSERT' THEN after->>'tenant_id'
        WHEN source = 'db' AND op = 'DELETE' THEN before->>'tenant_id'
        WHEN source = 'db' AND op = 'UPDATE'
          AND (before->>'tenant_id') IS NOT DISTINCT FROM (after->>'tenant_id')
          THEN after->>'tenant_id'
        WHEN source = 'app' THEN actor->>'tenant'
        ELSE NULL
      END
    ),
    occurred_at DESC,
    id DESC
  )
  WHERE (
    (source = 'db' AND (
      (schema_name = 'public' AND table_name IN ('invoice', 'line_item'))
    ))
    OR (source = 'app' AND op IN ('invoice.exported', 'invoice.sent'))
  );

ALTER INDEX auditstream.changes_tenant_feed_idx
  ATTACH PARTITION auditstream.changes_2026_11_tenant_feed_idx;

-- 3. Confirm parent index is valid (must return true; false means a partition was missed):
SELECT indisvalid
  FROM pg_catalog.pg_index
 WHERE indexrelid = 'auditstream.changes_tenant_feed_idx'::regclass;

-- 4. Update planner statistics as auditstream_owner, then restore role and revoke membership.
ANALYZE auditstream.changes;
RESET ROLE;
REVOKE auditstream_owner FROM migrator_role;
```

> **Failure recovery during online index builds:** Because these statements run outside a transaction, if any command errors, times out, or disconnects: (1) if reconnecting after a disconnect, run `SET ROLE auditstream_owner;`; (2) while still elevated as `auditstream_owner`, drop any half-built `INVALID` child index with `DROP INDEX CONCURRENTLY auditstream.<child_index>;` (or drop the parent shell with `DROP INDEX auditstream.changes_tenant_feed_idx;` without `CONCURRENTLY` if abandoning the build); (3) **then** run `RESET lock_timeout; RESET ROLE; REVOKE auditstream_owner FROM migrator_role;` so temporary `SET` membership is not left behind (which fails `auditstream verify` with `unsafe_privileges`).

Once `indisvalid` is `true`, PostgreSQL automatically creates matching child indexes on all future monthly partitions added by migrations or `auditstream verify --fix`.
Custom indexes on `auditstream.changes` do not conflict with `auditstream verify`.

### Verify index usage with `EXPLAIN (ANALYZE, BUFFERS)`

Always verify as `app_user` (never as a superuser, `BYPASSRLS` role, or `auditstream_owner`, who bypass RLS) that PostgreSQL selects `Index Scan` on your tenant index:

```sql
BEGIN;
SELECT pg_catalog.set_config('app.tenant', 't_001', true);
EXPLAIN (ANALYZE, BUFFERS)
SELECT id, occurred_at, schema_name, table_name, op, record_id, actor
  FROM auditstream.changes
 ORDER BY occurred_at DESC, id DESC
 LIMIT 50;
COMMIT;
```

Look for `Merge Append` over per-partition `Index Scan using ..._tenant_feed_idx` nodes with zero top-level `Sort`.
On tiny staging tables, PostgreSQL may still pick `Seq Scan`; test with realistic row counts (or run `SET LOCAL enable_seqscan = off;` inside the test transaction) to confirm the AST matches.
If `Seq Scan` persists, confirm `indisvalid = true`, run `ANALYZE auditstream.changes;` as `auditstream_owner` (or database owner/superuser), and compare PostgreSQL's deparsed `pg_get_expr(polqual, polrelid)` in `pg_catalog.pg_policy` against `pg_get_indexdef(indexrelid)` in `pg_catalog.pg_index`.

### Why `record_id` lookups bypass `changes_lookup_idx` under RLS

In PostgreSQL 15–19, `jsonb_eq`, `jsonb_contains`, and `jsonb_object_field_text` all have `proleakproof = false`.
Because RLS wraps `auditstream.changes` in a security barrier, PostgreSQL refuses to push a caller-supplied `WHERE record_id = $1::jsonb` predicate below the RLS barrier — bypassing the built-in partial hash index `changes_lookup_idx` (`USING hash (record_id) WHERE record_id IS NOT NULL`; see [ADR-0008](../decisions/0008-history-lookup-index.md)).
Marking a custom wrapper function `LEAKPROOF` is unavailable on managed PostgreSQL (RDS, Neon, Supabase) because `CREATE FUNCTION ... LEAKPROOF` requires true `SUPERUSER`.

Choose one of two v0.1.x workarounds depending on per-tenant history volume:

1. **Moderate per-tenant volume — composite tenant + table expression B-tree:**
   Put `table_name` right after the tenant expression in the partial expression index.
   Build it as `auditstream_owner` using the same online `ON ONLY` + per-partition `CONCURRENTLY` + `ATTACH PARTITION` (including `changes_default`) workflow above (or omit `ONLY` on an empty table), and confirm `indisvalid = true`.
   Keep this index *instead of* `changes_tenant_feed_idx` if all tenant queries filter by `table_name`, or *alongside* it only if you also run cross-table tenant activity feeds (each expression B-tree adds write maintenance cost):

   ```sql
   -- Run as auditstream_owner; follow with per-partition CONCURRENTLY + ATTACH (or omit ONLY on an empty table).
   CREATE INDEX changes_tenant_table_idx
     ON ONLY auditstream.changes (
       (
         CASE
           WHEN source = 'db' AND op = 'INSERT' THEN after->>'tenant_id'
           WHEN source = 'db' AND op = 'DELETE' THEN before->>'tenant_id'
           WHEN source = 'db' AND op = 'UPDATE'
             AND (before->>'tenant_id') IS NOT DISTINCT FROM (after->>'tenant_id')
             THEN after->>'tenant_id'
           WHEN source = 'app' THEN actor->>'tenant'
           ELSE NULL
         END
       ),
       table_name,
       occurred_at DESC,
       id DESC
     )
     WHERE (
       (source = 'db' AND (
         (schema_name = 'public' AND table_name IN ('invoice', 'line_item'))
       ))
       OR (source = 'app' AND op IN ('invoice.exported', 'invoice.sent'))
     );
   ```

   Because `texteq` is `LEAKPROOF`, PostgreSQL pushes `table_name` together with the tenant expression into `Index Cond`, narrowing the `record_id` heap filter strictly to that tenant's rows for that table.
   This accelerates `@auditstream/node`'s `audit.history()` (which filters `table_name` + `record_id` without `schema_name` or `occurred_at` bounds), `audit.query({ schemaName, table, recordId, since, until })`, and direct tenant-scoped SQL queries run inside an `app.tenant` transaction.
   Prefer `audit.query()` or time-bounded SQL with constant `occurred_at` bounds whenever possible so PostgreSQL also prunes monthly partitions.

2. **High per-tenant volume — fail-closed `SECURITY DEFINER` lookup wrapper owned by `auditstream_owner`:**
   Because the function runs as `auditstream_owner` (and `FORCE ROW LEVEL SECURITY` is disabled), PostgreSQL can hit `changes_lookup_idx` directly while the function enforces the exact same fail-closed allowlist, `app.tenant`, and cross-tenant `UPDATE` rules.
   Setting `plan_cache_mode = force_custom_plan` prevents PL/pgSQL generic-plan caching from disabling plan-time partition pruning on call 6+:

   ```sql
   BEGIN;
   -- Managed PostgreSQL 16+ migrator with ADMIN OPTION on auditstream_owner
   -- (omit GRANT/REVOKE if superuser; on PostgreSQL 15 use: GRANT auditstream_owner TO migrator_role;)
   GRANT auditstream_owner TO migrator_role WITH INHERIT FALSE, SET TRUE;
   SET LOCAL ROLE auditstream_owner;

   CREATE OR REPLACE FUNCTION auditstream.lookup_record_history(
     p_schema text,
     p_table text,
     p_record_id jsonb,
     p_since timestamptz DEFAULT '-infinity'::timestamptz,
     p_until timestamptz DEFAULT 'infinity'::timestamptz,
     p_limit int DEFAULT 50
   )
   RETURNS SETOF auditstream.changes
   LANGUAGE plpgsql
   STABLE
   SECURITY DEFINER
   SET search_path = pg_catalog, pg_temp
   SET plan_cache_mode = force_custom_plan
   AS $$
   DECLARE
     v_tenant text        := NULLIF(pg_catalog.current_setting('app.tenant', true), '');
     v_since  timestamptz := COALESCE(p_since, '-infinity'::timestamptz);
     v_until  timestamptz := COALESCE(p_until, 'infinity'::timestamptz);
     v_limit  int         := LEAST(GREATEST(COALESCE(p_limit, 50), 1), 1000);
   BEGIN
     -- Fail closed on missing tenant context, NULL inputs, or non-allowlisted tables.
     IF v_tenant IS NULL OR p_schema IS NULL OR p_table IS NULL OR p_record_id IS NULL THEN
       RETURN;
     END IF;
     IF (p_schema, p_table) NOT IN (('public', 'invoice'), ('public', 'line_item')) THEN
       RETURN;
     END IF;

     RETURN QUERY
       SELECT c.*
         FROM auditstream.changes AS c
        WHERE c.source = 'db'
          AND c.schema_name = p_schema
          AND c.table_name = p_table
          AND c.record_id = p_record_id
          AND c.occurred_at >= v_since
          AND c.occurred_at < v_until
          AND (
            CASE
              WHEN c.op = 'INSERT' THEN c.after->>'tenant_id'
              WHEN c.op = 'DELETE' THEN c.before->>'tenant_id'
              WHEN c.op = 'UPDATE'
                AND (c.before->>'tenant_id') IS NOT DISTINCT FROM (c.after->>'tenant_id')
                THEN c.after->>'tenant_id'
              ELSE NULL
            END
          ) = v_tenant
        ORDER BY c.occurred_at DESC, c.id DESC
        LIMIT v_limit;
   END;
   $$;

   REVOKE ALL ON FUNCTION auditstream.lookup_record_history(text, text, jsonb, timestamptz, timestamptz, int) FROM PUBLIC;
   GRANT EXECUTE ON FUNCTION auditstream.lookup_record_history(text, text, jsonb, timestamptz, timestamptz, int) TO app_user;

   SET LOCAL ROLE NONE;
   REVOKE auditstream_owner FROM migrator_role;
   COMMIT;
   ```

   Call it inside the tenant transaction after setting `app.tenant`, passing bounded constant timestamps whenever you have many monthly partitions:

   ```sql
   BEGIN;
   SELECT pg_catalog.set_config('app.tenant', 't_001', true);
   SELECT id, occurred_at, op, before, after, changed, actor
     FROM auditstream.lookup_record_history(
       'public',
       'invoice',
       '{"id": 100}'::jsonb,
       '2026-09-01T00:00:00Z'::timestamptz,
       '2026-10-01T00:00:00Z'::timestamptz,
       50
     );
   COMMIT;
   ```

   > **Security and `verify` boundary for custom `SECURITY DEFINER` wrappers:** Because `auditstream.lookup_record_history` executes as `auditstream_owner`, it bypasses table-level RLS policies on `auditstream.changes` and is **not** inspected by `auditstream verify` (which audits only `resolve_actor`, `capture`, and `log_event` — never overload those three names, or `verify` reports `tampered_history`). Keep its allowlist, tenant predicate, and `EXECUTE` ACLs strictly synchronized with `changes_tenant_select` and any `RESTRICTIVE` policies.

## Step 4: Configure CLI RLS guards (`verify` and `export`)

- **`auditstream export` fails closed under RLS (`v0.1.1+`):** Always connect `auditstream export` (and operator `auditstream history` CLI inspections) as `auditstream_exporter`. If `export` runs as `app_user` (or any non-bypass role lacking an unobstructed `PERMISSIVE USING (true)` policy and zero blocking `RESTRICTIVE` policies), it exits with code `3` before opening the output file or advancing the cursor. Pass `--allow-rls-filtered` only when an intentionally RLS-filtered export is desired. See [`auditstream export`: Row-Level Security (RLS) guard](../reference/cli/export.md#row-level-security-rls-guard).
- **`auditstream verify` audits RLS safety in CI (`v0.1.1+`):** List **only** your tenant-scoped runtime application roles in `capture.app_roles` (do not add `migrator_role`, `auditstream_exporter`, or `auditstream_verify`; note CLI `--app-role` replaces `capture.app_roles`):

  ```toml
  [capture]
  tables = ["public.invoice", "public.line_item"]
  app_roles = ["app_user"]
  ```

  Run read-only CI checks as `auditstream_verify` with `auditstream verify --fail-on warning`. It catches `forced_rls` (`error`), `rls_without_select_policy` (`error`), `rls_hides_default_partition` (`warning`), and `rls_bypassed_by_app_role` (`warning`). For scheduled partition maintenance (`auditstream verify --fix`), use a separate migration job authorized under `auditstream_owner` with default `--fail-on error` (on Amazon RDS, a `NOBYPASSRLS` migration role without a `USING (true)` policy emits the advisory `rls_hides_default_partition` warning during post-fix verification; see [Check triggers in CI with `verify`](verify-in-ci.md)).

## Step 5: Poolers, serverless drivers, and partition pruning

### Connection poolers and serverless platforms

- **PgBouncer (transaction mode), Supavisor, and Neon pooler:** Always set tenant context inside an explicit transaction with `is_local = true`:

  ```sql
  BEGIN;
  SELECT pg_catalog.set_config('app.tenant', $1, true);
  -- Run tenant-scoped SELECT queries here
  COMMIT;
  ```

  Never run session-level `SET app.tenant = ...`, which leaks tenant identity across pooled client connections.
- **AWS RDS Proxy:** Calling `set_config('app.tenant', ..., true)` pins the server session behind RDS Proxy. Keep trailing SQL comments for write attribution, and evaluate dedicated tenant-read connections or a direct RDS endpoint if pinning reduces connection multiplexing.
- **Neon HTTP and JWT auth:** Stateless single HTTP queries cannot carry `set_config` across requests. Either execute `set_config('app.tenant', $1, true)` and the `SELECT` together in one Neon HTTP batch transaction (`sql.transaction([...])`), or authenticate with JWT claims verified server-side:
  - **Neon Authorize (`pg_session_jwt`):** replace `NULLIF(pg_catalog.current_setting('app.tenant', true), '')` in `changes_tenant_select` (and `lookup_record_history` if used) with `NULLIF(auth.session()->>'tenant_id', '')` (adjust the claim key to your JWT schema).
  - **Supabase / PostgREST:** replace it with `NULLIF(NULLIF(pg_catalog.current_setting('request.jwt.claims', true), '')::jsonb->>'tenant_id', '')` — wrapping `current_setting` in `NULLIF(..., '')` **before** casting to `jsonb` prevents SQLSTATE `22P02` errors when pooled sessions reset the GUC to `''`. Always read the tenant claim from a server-controlled JWT field (such as a Custom Access Token Auth Hook claim or `app_metadata`, never client-writable `user_metadata`).

See [Run on Neon or Supabase](run-on-neon-and-supabase.md) for platform migration and pooler details.

### Constant timestamps for partition pruning

Always pass **application-computed constant RFC 3339 timestamps** when filtering `occurred_at` across many monthly partitions — never `STABLE` expressions such as `now() - interval '90 days'`:

```sql
-- GOOD: enables plan-time partition pruning before locking untouched partitions
SELECT id, occurred_at, table_name, op, record_id
  FROM auditstream.changes
 WHERE occurred_at >= '2026-08-29T00:00:00Z'::timestamptz
 ORDER BY occurred_at DESC, id DESC
 LIMIT 50;

-- AVOID at high partition counts: STABLE now() locks all partitions before runtime pruning.
-- WHERE occurred_at >= now() - interval '90 days'
```

At 120 monthly partitions under 64 concurrent clients, constant timestamps avoid `LWLock:LockManager` lock contention and run `26×–28.5×` faster than `now() - interval '90 days'`.
When detaching and dropping old monthly partitions manually (automated commit-safe `auditstream prune` is planned for v0.2 in [#145](https://github.com/auditstream/auditstream/issues/145)), ensure every unfiltered export cursor **and its saved boundary `anchor` row** have already advanced into a newer partition — dropping a partition still holding a cursor's `anchor` aborts the next `auditstream export` resume with exit code `3`.
See [How capture works: Partition scaling and constant `occurred_at` timestamps](../explanation/how-capture-works.md#partition-scaling-and-constant-occurred_at-timestamps) for full benchmark evidence and PostgreSQL 15–17 fast-path lock details.

## Forward compatibility note for v0.2

Row-data RLS (`after->>'tenant_id'` and `before->>'tenant_id'`) relies on full row images on `UPDATE` (the only storage mode in v0.1.x).
It is **incompatible** with the planned v0.2 opt-in per-table `diff` storage mode ([#166](https://github.com/auditstream/auditstream/issues/166)), which stores only changed column keys in `before` and `after` and omits unchanged `tenant_id` keys on `UPDATE`.

Multi-tenant deployments that plan to adopt v0.2 `diff` mode — or eliminate the `jsonb_eq` RLS lookup wall without a `SECURITY DEFINER` wrapper — should migrate to v0.2's planned first-class nullable `tenant_id` and leakproof `record_id_hash` columns ([#167](https://github.com/auditstream/auditstream/issues/167)) when available.
