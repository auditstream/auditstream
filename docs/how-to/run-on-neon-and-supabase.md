# Run on Neon or Supabase

Auditstream v0.1 is verified on Neon (PostgreSQL 18) and Supabase (PostgreSQL 17), including transaction-mode poolers.

## Migrations as a non-superuser (`CREATEROLE`)

Managed PostgreSQL services run migrations as a non-superuser role with `CREATEROLE`.
On PostgreSQL 16 and newer, creating `auditstream_owner` grants `ADMIN` without `INHERIT` or `SET`.
Migrations generated by `auditstream init` (and `auditstream verify --fix`) check `pg_has_role` for the missing `SET` / `USAGE` (`MEMBER` on PostgreSQL 15) options, temporarily self-grant only what is needed inside the transaction, create and harden objects as `auditstream_owner`, and revoke only the temporary grant before committing.

Run migrations and `auditstream verify --fix` using your direct (non-pooled) migration connection string with a transactional migrator (such as Drizzle's Neon WebSocket `neon-serverless` migrator, `node-postgres`, `postgres.js`, Prisma Migrate, or `psql`).
Stateless per-statement runners such as the Drizzle Neon HTTP migrator are not supported for applying migrations because migrations require a single transaction for lock bounds, DDL atomicity, and revoking the temporary `auditstream_owner` self-grant; generated migrations stop before DDL if executed outside a transaction.
See [Migration lock waits](../reference/cli/init.md#migration-lock-waits).

## Connection poolers

- **Neon pooler, Supavisor, and PgBouncer (transaction mode):** both trailing SQL comments and transaction-local `set_config(..., true)` work with zero actor leakage across concurrent requests.
- **Neon HTTP and WebSocket drivers:** use `@auditstream/drizzle/neon-http` or `@auditstream/prisma` with `@prisma/adapter-neon`; both carry comments and `set_config` intact.
- **AWS RDS Proxy:** use the trailing SQL comment transport. Calling `set_config(..., true)` pins the server session behind RDS Proxy.

## Supabase JWT fallback

When neither `set_config('auditstream.actor', ..., true)` nor a trailing `/*auditstream='...'*/` comment is present, `auditstream.resolve_actor()` inspects `request.jwt.claims`.
If `request.jwt.claims` is a valid JSON object containing a non-empty `sub` string, Auditstream records:

```json
{"type":"user","id":"<sub>"}
```

with `actor_source = 'jwt'`.
PostgREST and Supabase client requests therefore carry the authenticated user ID automatically without extra SQL comments.

## Least-privilege application role

Grant your runtime application role read-only access to history and execute access to `log_event`:

```sql
GRANT USAGE ON SCHEMA auditstream TO app_user;
GRANT SELECT ON auditstream.changes TO app_user;
GRANT EXECUTE ON FUNCTION auditstream.log_event(text, jsonb, jsonb) TO app_user;
```

Do not grant `INSERT`, `UPDATE`, `DELETE`, or `TRUNCATE` on `auditstream.changes` to the application role.
`auditstream history` and `auditstream export` both work with `SELECT`-only access on `auditstream.changes`.

## Multi-tenant Row-Level Security (RLS)

Default admin roles on Neon (`neondb_owner`, `neon_superuser`) and Supabase (`postgres`, `service_role`) carry `BYPASSRLS` and silently bypass RLS, while Amazon RDS disallows `BYPASSRLS` on customer admin roles (`rds_superuser`).
For portable, least-privilege multi-tenant RLS on `auditstream.changes`:

- Create a dedicated `NOSUPERUSER NOBYPASSRLS` `app_user` via SQL for runtime queries, and dedicated `NOSUPERUSER NOBYPASSRLS` `auditstream_exporter` and `auditstream_verify` roles with `PERMISSIVE` `SELECT` policies `USING (true)` and zero `RESTRICTIVE` policies. Connect `auditstream export` as `auditstream_exporter` (connecting as `app_user` fails closed with exit code `3` under RLS).
- Enable `ALTER TABLE auditstream.changes ENABLE ROW LEVEL SECURITY;` as `auditstream_owner` — never `FORCE ROW LEVEL SECURITY` (which breaks `SECURITY DEFINER` capture writes), never grant `SELECT` on child partitions, and scope tenant policies `TO app_user` (never `TO PUBLIC`).
- On Neon's stateless HTTP driver, run `set_config('app.tenant', $1, true)` and the `SELECT` together inside one HTTP batch transaction (`sql.transaction([...])`), or use Neon Authorize (`pg_session_jwt` `auth.session()`) / Supabase JWT claims (`request.jwt.claims`) and update the RLS policy's right-hand side to match.

See [Isolate tenants with Row-Level Security (RLS)](multi-tenant-rls.md) for the complete row-data RLS policy, AST-matched expression index, `record_id` lookup workarounds, and `verify`/`export` RLS guards.
